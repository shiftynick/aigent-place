## Medium: pre-durable results and ignored writer errors

The concern is factually correct and remains a material product-contract deviation. ADR-0005:104-122 requires accepted/rejected results, cursors and idempotency mappings in the same durable transaction, and result delivery only after commit/install. Protocol contract:114-127 requires the admission boundary before any authoritative exact-next result. Replay contract:233-241 requires global command shutdown and verified recovery after writer failure. The local callback is explicitly not that complete durable pipeline.

The generic result-before-commit loss mechanism and writer failure transitions are unchanged from base:

- Base transport.rs:1092-1095 caches an in-memory SessionHub outcome, 1108-1116 queues its effect, and 1119-1124 admits its result to outbound without a durable acknowledgment. Final transport.rs:1089-1107 synchronously queues before caching, then 1125-1129 uses the same immediate outbound delivery. The repair improves local enqueue/caching atomicity; it does not add any durable acknowledgment check.
- Base transport.rs:656-674 and final transport.rs:659-677 have the same three discarded failure paths: initial durable poll, second poll inside Submitted/Busy, and tick advance. There is no new writer-unavailable state, failure-to-Conflict conversion, global close, or cache rollback on writer error.
- Base world.rs:777-784 and final world.rs:818-825 restore original and later pending commands after async writer error. The implementation is unchanged except line movement. Those branches never alter SessionHub.
- Final world.rs:723-734 persists world state and command summaries, not SessionHub results/cursors/idempotency records. Persist and main sources have no final diff. Startup still passes a fresh SessionHub::new_v1 into world recovery (main.rs:92-93; transport.rs:202-210).

An exact common loss schedule is reachable at both base and final: with pressure equal to the current unstarted world tick T, send a valid new MOVE; receive Accepted; submit its T generation; let the writer fail; crash before any successful retry; restart from the last committed world generation. The acknowledged MOVE and its in-memory result/key are absent at both revisions. Final admission removes the earlier local-drop case but does not create this storage/crash loss schedule. Moving storage-paused arrivals to T+1 can change which failed generation contains an effect; it does not create a result-loss mechanism that base lacked, because base had already acknowledged that still-uncommitted future command too.

The new typed Conflict does need an explicit caveat. It is inserted into both RAM indexes at final session.rs:613-629, after queue rejection at transport.rs:1184-1188, and has no world record. A writer failure alone does not erase it: same-process reconnect/replay retains Conflict, including after the pending collider disappears. It does not change any writer-failure branch. The existing live-Hub tests prove that behavior (listen_journal_behavior.rs:480-632), not restart recovery.

There is nevertheless a new observable rejection outcome that can be lost on restart: during a sealed Busy generation, E1 MOVE seq1/key K1 queues at T+1; E2 STOP seq1/new key K2 receives Conflict; then the process stops or crashes and restarts, losing K2 and its pending collider; E3 retries STOP seq1/K2 and receives Accepted. At base, choose an intervening pressure advance: K2 returns Accepted before and after restart rather than Conflict then Accepted. Thus, do not claim every observable outcome is unchanged. The new Conflict adds a new instance of undurable authoritative-result loss to the existing incomplete result/idempotency recovery surface.

That outcome-flip class already existed at base independently of the new callback: cache K1/MOVE, reconnect and send STOP under K1; base session.rs:565-568 returns IdempotencyConflict; restart with the fresh hub and retry the same STOP/K1 and it can be Accepted. Unsupported/invalid and no-effect results also lack durable recording. The new callback does not introduce the missing durable result store or a lost queued effect on an otherwise correct local admission schedule, as the first-round batching collision did.

Recommendation: retain the medium concern as confirmed, explicitly tracked residual durable-pipeline debt. Do not describe it as fully solved, dismiss it merely because paths existed, or promise crash-stable Conflict from these tests. Document the new Conflict restart limitation as part of that debt. Do not remove typed Conflict or expand this bounded task into the full durable pipeline solely to hide the concern: the operator-approved task-064 amendment explicitly requires live sequence/cross-epoch Conflict stability and forbids global durable-failure expansion. Root must own the scope adjudication; this is not a cold-review pass or a change to the accepted contract.
